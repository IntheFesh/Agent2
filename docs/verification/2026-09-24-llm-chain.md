## 2. 协议探针（后端兼容性检查，不是链路演示）

目的：Phase 12 第 4 条要求兼容性问题只能在 `src/workbench/llm/` 中修复。按 §1.1 的文档，本仓库在 DeepSeek 默认的思考模式下应当在第二次 act 调用时失败；而三条链路都只能执行一次（N2），不能拿它们来试错。因此先用极小的请求直接检验协议。P1–P3 共 6 个请求，记账 ¥0.0589；P4 为 1 个请求，¥0.0044（上界口径）。

| 探针 | 方式 | 结果 |
|---|---|---|
| P1 | 本仓库 `OpenAICompatBackend`（流式），DeepSeek 默认思考模式，1 个无参数工具；第 2 个请求像 act 节点一样不带 `reasoning_content` | 两个请求都成功：第 1 个返回原生 `tool_calls`（25 个输出 token），第 2 个给出最终回答 |
| P2 | 同一后端，`extra_body` 传 `{"thinking": {"type": "disabled"}}`，工具为官方 `e_commerce_33` 的 39 个真实工具 schema | 两个请求都成功；DeepSeek 接受全部 39 个 schema（第 1 个请求 13,248 个输入 token），返回 `e_commerce_33__list_product_categories` 调用 |
| P3 | 原始 HTTP 流式请求，显式 `{"thinking": {"type": "enabled"}}`；第 1 个请求确实产生了思考内容（`reasoning_content` 425 个字符，`reasoning_tokens` 123），第 2 个请求不带 `reasoning_content` | 第 2 个请求仍返回 HTTP 200 |
| P4 | OpenAI Python SDK 2.38.0（与 AWM 相同的调用方式），`max_completion_tokens=16`（`awm agent` 与 `awm verify` 都用这个参数：`awm/core/agent.py:370`、`awm/core/verify.py:309`） | 请求被接受，但参数不生效：输出 536 个 token（其中思考 token 246 个），`finish_reason` 为 `stop` |

结论：

- **工具调用格式兼容**：DeepSeek 在流式响应中返回原生 `tool_calls`，本仓库后端能正确解析；最后一个 chunk 中的 `usage` 也能正确读取。
- **文档要求与实测不一致**：文档说不回传 `reasoning_content` 会得到 400，2026-09-24 17:02 UTC 的实测没有出现 400。本仓库没有修改代码：工具调用格式本身是兼容的，不满足 Phase 12 第 4 条"不兼容"的前提；但也不应依赖这种与文档不符的宽松行为。这是一个外部风险：DeepSeek 一旦按文档执行，act 节点在第一次工具调用之后的请求会得到 HTTP 400（`LLMRequestError`，不重试），智能体以 `llm_error` 终止。已记入 LIMITATIONS。
- 输出 token 包含思考 token（P3：184 个输出 token 中 123 个是思考 token）。
- `max_completion_tokens` 被接受但被忽略（P4）：AWM 的 `--max_tokens`（agent，默认 2048）与裁判调用的 4096 上限（verify）对 DeepSeek 都不生效，单次输出只受服务端默认值约束。本仓库后端发送的是文档中的 `max_tokens`，不受影响。

## 4. `awm agent`（Phase 12 第 3 步，只执行 1 次）

### 4.1 运行方式：`--mcp_url` 模式

`awm agent` 支持两种方式（RECON §1.3）。本次没有用 `--scenario` 自动起服，而是由本仓库 env-manager 启动官方 `e_commerce_33`（会话 `p12awm`，启动参数显式传了 `--db_path`、`--temp_server_path`、`--output_dir`），再把 `--mcp_url` 交给 `awm agent`，同时传 `--scenario e_commerce_33 --task_id 0`，让任务从 `--tasks_path` 查出、并写进 `trajectory.json`（`awm/core/agent.py:398-407,433-458`）。原因是自动起服有三个上游问题，都无法在不改上游的前提下绕开：

1. **结束时必然抛 `shutil.SameFileError`**（新发现，已用不调用 LLM 的方式复现）：`_prepare_database` 把工作库直接建成 `<output_dir>/final.db`（`awm/core/server.py:70-82`），运行结束时 `run_agent` 又把它复制到同一路径 `<output_dir>/final.db`（`awm/core/agent.py:596-598`）。`trajectory.json` 已经保存，但命令会以异常退出。
2. 自动起服的 `start_server_process`（`awm/core/server.py:174-195`）不传 `--temp_server_path`，服务代码会写到 `--envs_path` 所在目录（`awm/core/server.py:134-138`），指向官方数据时就会写进 `data/awm1k/`。
3. 结束时只终止启动器进程（`awm/core/agent.py:603-612`），真正的服务进程会残留（RECON §10 Phase 2 实测）。

`--mcp_url` 模式不在输出目录保存数据库，因此 `awm verify` 需要显式传 `--init_db_path` / `--final_db_path`（`awm/core/verify.py:41-43,367-368`）。

命令（`OPENAI_API_KEY` 只在该进程环境中由 `DEEPSEEK_API_KEY` 映射）：

```
awm agent --scenario e_commerce_33 --task_id 0 --tasks_path data/awm1k/gen_tasks.jsonl \
  --mcp_url http://127.0.0.1:18100/mcp --api_url https://api.deepseek.com --model deepseek-flash \
  --output_dir data/p12/awm-agent/e_commerce_33_task_0
```

其余参数保持上游默认（`max_iterations` 30、`temperature` 1.0、`max_tokens` 2048）。`api_url` 不含 `localhost`，因此不附加 vLLM 专用参数（`awm/core/agent.py:417`）；DeepSeek 以默认的思考模式运行。

### 4.2 结果：第 2 轮输出格式不兼容，循环提前结束

| 轮次 | 模型输出 | AWM 的处理 |
|---|---|---|
| 1 | `<tool_call>{"name": "list_tools", "arguments": null}</tool_call>`（符合 AWM system prompt 规定的格式） | 解析成功，返回 39 个工具的清单（31,834 个字符） |
| 2 | `<｜｜DSML｜｜ calls><｜｜DSML｜｜ invoke name="call_tool">{"tool_name": "mcp_tool_mcp_server_search_products", "arguments": "{…\"max_price\": 200, \"sort_by\": \"average_rating\", \"limit\": 20}"}</｜｜DSML｜｜ parameter></｜｜DSML｜｜ invoke></｜｜DSML｜｜ calls>` | AWM 只识别 `<tool_call>…</tool_call>`（`awm/core/agent.py:130-167`），解析出 0 个工具调用，于是把这段文本当成最终回答，循环结束（`awm/core/agent.py:506-518`） |

- 退出码 0，总耗时 `real 0m6.942s`，共 2 次 LLM 请求。`trajectory.json` 的顶层字段与 RECON §1.5 一致：`scenario, task_id, task, model, api_url, max_iterations, temperature, total_iterations, timestamp, trajectory, messages`。
- 会话数据库没有变化（`workbench env diff p12awm` → `changed: false`），没有发生任何写操作。
- 结论：链路的前半段（DeepSeek 调用 → 文本解析 → MCP 工具清单）打通；第 2 轮起 DeepSeek 在纯文本里输出了它自己的工具调用标记（DSML），与 AWM 的 `<tool_call>` 文本协议不兼容。按仓库主人的决定 D3，只如实记录，不修改上游，也不写适配器。这是单次运行中观察到的现象，不代表每次都会这样，也不构成对任何模型的评价。
